# 卒業制作 チーム開発計画

## 1. 開発の基本方針

- Flutter/Dartの1コードベースからAndroidとWebを提供する
- `features/` 単位で担当を分け、同じファイルへの同時編集を減らす
- 画面だけ、APIだけを別々に長期間作らず、「モデル → 保存 → 状態管理 → 画面 → テスト」を小さな機能単位で完成させる
- 外部APIはRepositoryの裏側へ隠し、開発中はモックデータでも画面を確認できるようにする
- `main` ブランチは常に起動可能な状態を維持する

## 2. 推奨ディレクトリ構成

```text
lib/
├─ app/                    # アプリ起動、テーマ、ルーティング
├─ core/                   # 複数機能で共用するAPI、保存、位置情報、共通Widget
└─ features/
   ├─ schedule/            # 予定作成・一覧・詳細
   │  ├─ domain/           # モデル、Repositoryのインターフェース
   │  ├─ data/             # 保存/API実装、DTO
   │  └─ presentation/     # page、provider、widget
   ├─ home/
   ├─ calendar/
   ├─ weather/
   ├─ transportation/
   ├─ map/
   ├─ group/
   ├─ account/
   └─ settings/
test/
├─ unit/                   # モデル、計算、Repository
├─ widget/                 # 画面部品
└─ integration/            # 予定作成などの一連の操作
docs/                      # 仕様、進捗、チーム内の決定事項
```

現在作成済みの `features/` 構成を継続する。空ファイルは将来規模の見本なので、担当機能に着手した時点で必要なものだけ実装する。

## 3. 制作順序

### フェーズ1: 予定機能を縦に完成させる

1. `ScheduleRepository` のインターフェース
2. ローカル保存実装
3. 予定の追加・取得・更新・削除テスト
4. 予定作成画面
5. 予定一覧・詳細画面

最初にこの流れを完成させ、アプリ内に実データが流れる基準形を作る。

### フェーズ2: アプリの骨格

1. ルーティング
2. HOME・マップ・カレンダー・マイページのボトムナビゲーション
3. レスポンシブ表示
4. ライト／ダークテーマ切替

### フェーズ3: 予定データを各画面へ連携

1. HOMEの直近予定
2. カレンダーの日付表示
3. 次の移動情報
4. 過去予定の表示制御

### フェーズ4: 外部サービス

1. Open-Meteoによる天気
2. 地図・経路表示
3. ODPTによる運行情報
4. 位置情報と権限処理

APIごとにモック実装を先に用意し、API停止中でも開発できるようにする。

### フェーズ5: 発展機能

1. AI旅程提案
2. グループ共有
3. カレンダー連携
4. 通知・リマインダー

卒業制作の期限に応じ、ここは優先順位を付けて実装範囲を調整する。

### フェーズ6: 品質確認と提出

1. Android実機・iPhone向けWeb・PCブラウザで確認
2. エラー表示、ローディング、空状態を確認
3. テスト追加、操作動画、スクリーンショット、README作成
4. リリース用Android APK/AABとWeb版を生成

## 4. チームの担当分け

3人の場合の例:

- A: 予定・カレンダー・ローカル保存
- B: HOME・天気・交通情報
- C: 地図・設定・レスポンシブUI

全員が同時に `app.dart` や `router.dart` を変更しないよう、共通ファイルの担当者を1人決める。AI、グループ、通知は基本機能が動いた後に再分担する。

## 5. Git運用

- `main`: 動作確認済みだけを置く
- 機能ブランチ: `feature/schedule-create`、`feature/weather-api` のように1機能1ブランチ
- 修正ブランチ: `fix/android-build` のように目的を明確にする
- 作業開始前に最新の `main` を取り込む
- 1つのPull Requestを小さくし、担当外のメンバーがレビューする
- APIキー、署名ファイル、個人設定はコミットしない

## 6. Pull Requestの完了条件

- AndroidまたはWebで対象機能を操作できる
- `dart format` 済み
- `flutter analyze` が成功する
- 関連する `flutter test` が成功する
- 新しい仕様・判断を `docs/PROJECT_PROGRESS.md` に記録する
- UI変更にはスクリーンショットを添付する

## 7. 最初の短期目標

最初の1〜2週間は「予定を作成し、保存し、再起動後も一覧とカレンダーに表示できる」状態を目標にする。この完成後、天気・地図・ODPTを並行開発へ移す。
